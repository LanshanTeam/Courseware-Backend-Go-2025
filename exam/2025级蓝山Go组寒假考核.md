欢迎参加 Go 组寒假考核。本次考核旨在评估各位的编程能力、学习能力以及独立思考能力。本次考核并不会实行筛选，因为寒假考核主要是做一次阶段性测试，通过做一个完整的后端项目来帮助大家理解有什么地方还是不足的，需要弥补的。

# 传统选题

## 知乎社区

做一个类似 Quora/zhihu 的在线问答/发帖社区项目。

### 基本要求

1. 基本的用户系统

   1. 用户的注册与登录。
   2. （**非必要**）用户的基本信息如头像、个人简介等内容。
   3. 基本的用户鉴权。
   4. （**非必要**）密码的加盐加密。
   5. 用户个人信息的修改
2. 发布文章、问题；以及能够进行问题的回答、文章的评论。

   1. 发布/删除/更新/获取文章、问题（可以只做一个）
   2. （**非必要**）文章格式建议规范为markdown，且文章可以插入图片（存储参考网盘项目的文件上传部分）
   3. 能够对文章、问题进行回复/评论
   4. （**非必要**）对问题进行关注、可以对文章、问题回答进行点赞和收藏。
   5. （**非必要**）按照问题热度进行排序，做一个热度榜
3. 关注用户，并能够接收关注的人的动态，(**非必要**)对用户下发通知

   1. 关注用户和取消关注
   2. 关注列表和关注者列表。
   3. （**非必要**）可以接收已关注用户的所有动态，如果要做的话建议看看b站上朋友圈/微博 feed 流的设计。
4. 内容的搜索，可以使用 MySQL 的全文索引来做。（**进阶，推荐做**）

   1. 使用 MySQL 的全文索引实现搜索功能。
5. 文章状态(草稿，已删除，未删除)
6. 管理员禁言
7. 防刷机制(点赞频率，评论频率)



### 进阶要求

1. 加入缓存策略

   1. 对基本的文章内容等数据进行缓存，并采取合理的缓存策略。
   2. 使用 go 内置的 singleflight、布隆过滤器等来应对缓存击穿、缓存雪崩这些问题。
2. Docker 打包、部署和安全

   1. 通过编写 dockerfile 文件来将项目打包成镜像。
   2. 推送到 dockerhub 或其他的镜像仓库上。
   3. 部署到自己的服务器上。
   4. 考虑防止 XSS、SQL 注入、CSRF 等常见安全风险。
3. 接口文档以及前端界面

   1. （**强烈建议！！！**）使用 apifox、apipost 等工具保存接口文档。
   2. 借助 agent 工具如 copilot、codex 等扫描你的代码并生成前端界面，便于调试。
4. 站内通知和私信

   1. 互相关注的人可以互相发送消息私信。
   2. 当关注的问题或者有人回复你的评论会发送站内通知。
5. 盐选会员

   1. 加入会员的角色管理。
   2. 非会员只能访问某些文章的部分内容。
6. 文章推荐和内容总结

   1. 可以通过接入大模型实现。
   2. 每个文章的总结只需要生成一次即可，后续均访问该缓存，当更新的时候可以重新生成内容。
   3. 文章推荐可以选择调大模型接口做智能推荐，这里不做重点要求，因为一般是算法干的事。
7. 配置管理和日志管理

   1. 通过 viper 或者其他方式加载如 mysql 相关信息的配置文件
   2. 通过 zap、zerolog 等专门的日志库集成日志。
8. 内容分发与访问加速方案等

## 百度网盘

仿百度网盘的一个项目，目标是实现文件云存储、文件共享等功能

### 基本要求

1. 基本的用户系统

   1. 用户的注册与登录。
   2. （**非必要**）用户的基本信息如头像、个人简介等内容。
   3. 基本的用户鉴权。
   4. （**非必要**）密码的加盐加密。
   5. 个人信息的修改
2. 文件上传、文件删除、文件共享

   1. 使用本地磁盘挂载或者对象存储服务（如云厂商、minio）实现文件存储的功能。
   2. 通过数据库保证文件的元数据管理。
   3. 可以为文件生成共享链接供他人下载，需要支持密钥访问的功能。
3. 个人文件和存储空间管理

   1. 要求实现个人的存储空间使用情况以及限额。
   2. 能够查看个人存储的文件元数据等基本信息。
4. 共享文件的收藏

   1. 当用户具有访问该文件的权限的时候，可以执行收藏操作，用户可以查看自己的收藏列表。
5. 最近删除

   1. 删除进回收站，支持彻底删除/恢复



### 进阶要求

1. 加入缓存策略

   1. 对文件元信息、存储额度等数据进行缓存，并采取合理的缓存策略。
   2. 使用 go 内置的 singleflight、布隆过滤器等来应对缓存击穿、缓存雪崩这些问题。
2. Docker 打包、部署和安全

   1. 通过编写 dockerfile 文件来将项目打包成镜像。
   2. 推送到 dockerhub 或其他的镜像仓库上。
   3. 部署到自己的服务器上。
   4. 考虑防止 XSS、SQL 注入、CSRF 等常见安全风险。
3. 接口文档以及前端界面

   1. （**建议**）使用 apifox、apipost 等工具保存接口文档。
   2. 借助 agent 工具如 copilot、codex 等扫描你的代码并生成前端界面，便于调试。
4. 实现下载限速

   1. 加入一个会员的角色
   2. 对于非会员用户通过一定手段实现限速下载。
5. 断点续传和分块上传

   1. 实现断点续传和分块上传，后端只需要处理拼接逻辑和上传进度的状态管理就可以了，完整的功能通常需要前后端协作。
6. 配置管理和日志管理

   1. 通过 viper 或者其他方式加载如 mysql 相关信息的配置文件
   2. 通过 zap、zerolog 等专门的日志库集成日志。
7. 文件，图片等预览

   1. 图片预览、PDF/文本预览（前端部分）
8. 配额

   1. 用户空间配额管理，和前面提到的会员配套
9. 搜索

   1. 以大小，创建时间等排序
   2. 支持创建标签辅助搜索
10. 敏感内容上传检查

# 特殊选题

## 弓箭手大作战

设计并实现一个平面的 2D 射击游戏后端，效果类似[弓箭手大作战](https://www.taptap.cn/app/29462?os=android)，对前端/客户端有很强的依赖性，建议至少有能力使用 agent 搓前端/客户端的人选择。

### 基本要求

1. 基本的用户系统

   1. 用户的注册与登录。
   2. （**非必要**）用户的基本信息如头像、个人简介等内容。
   3. 基本的用户鉴权。
   4. （**非必要**）密码的加盐加密。
   5. （**非必要**）玩家的段位、积分排行
2. 房间的状态管理

   1. 统计房间对局的玩家评分。
   2. 地图管理，可以随机生成，也可以是固定地图。
   3. 各个玩家的实时位置同步到后端存储。
   4. 玩家生命值等状态管理。
   5. （**非必要**）房间内临时对话。
   6. （**非必要**）对局的断线重连。
3. 实时对战（可以用 websocket）

   1. 通过 websocket，服务端实时推送当前房间内的状态和对方玩家的位置，实在不行也可以用轮询。
   2. 客户端将玩家位置推送到服务端，用于更新房间内玩家状态。
   3. （**非必要**）作弊检测，比如瞬移、穿墙等外挂需要检测。
   4. （**非必要**）两人以上的多人混战
   5. 子弹、箭矢等投掷物的实时更新。
   6. （**非必要**）场内道具、buff、debuff。



### 进阶要求

1. 性能优化

   1. 作为一个实时对战游戏，性能要放在第一位，尝试使用多级缓存（本地->分布式缓存->数据库）
   2. 思考并解决多级缓存的一致性问题。
2. Docker 打包、部署和安全

   1. 通过编写 dockerfile 文件来将项目打包成镜像。
   2. 推送到 dockerhub 或其他的镜像仓库上。
   3. 部署到自己的服务器上。
   4. 考虑防止 XSS、SQL 注入、CSRF 等常见安全风险。
3. 接口文档以及前端界面

   1. （**建议**）使用 apifox、apipost 等工具保存接口文档。
   2. 借助 agent 工具如 copilot、codex 等扫描你的代码并生成前端或者客户端，便于调试。
4. 自定义应用层网络协议实现游戏对局的高性能传输。（比较复杂、而且需要额外一个网关适配浏览器的协议或者用非网页端才行）

   1. 比较简单的做法是基于现有的 TCP 框架比如 [zinx](https://github.com/aceld/zinx) 去实现全双工的通信。
   2. 如果追求极致的性能，可以尝试用 [gnet](https://github.com/panjf2000/gnet) 或者 go 内置的 net 包自己实现解决粘包问题和路由策略。
5. 限流策略

   1. 通过本地内存或者 redis 做一个限流策略，防止服务端承受过大的压力。
   2. 比如可以根据玩家消息发送频率、服务端可以承受的请求数量等进行限流。
6. 配置管理和日志管理

   1. 通过 viper 或者其他方式加载如 mysql 相关信息的配置文件
   2. 通过 zap、zerolog 等专门的日志库集成日志。
7. 弱网优化，断线重连
8.  回放，重放功能
